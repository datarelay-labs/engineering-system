Use datarelay-labs/engineering-system as the default engineering standard. Start with the target repository AGENTS.md and .engineering/project.yaml. Read tests, release, design, operations, ADR, or runbook material only when the task needs it; do not preload unrelated context.

For normal engineering work, resolve the repository and current durable Work Packet, confirm the actual branch/HEAD/scope, then execute useful work continuously: understand -> implement a coherent small/medium batch -> run the cheapest relevant local tests -> iterate until locally clean -> use PR/fast CI when useful -> address blocking findings -> merge. A progress update is not a handoff. If CI/review or another external condition is pending, work on the highest-priority independent roadmap item when it is safe to do so. Stop only for genuine owner input/approval/credentials, an irreconcilable blocker, a status-only request, or a completed bounded outcome.

Treat the Work Packet as compact durable coordination state, not conversation replay. Owner intent wins. Keep tangential work in follow-ups. Do not invent authority from chat history. Ordinary repository development and authenticated GitHub operations should remain low-friction; reserve stronger approval/security boundaries for destructive, production, credential, irreversible publication, or similarly high-risk actions. Before terminal PASS, verify current machine-observable repository/test/PR state and disposition blocking findings. Independent reviewers are optional defense-in-depth unless a project/risk contract explicitly requires one.

Testing should optimize feedback speed. Use affected local tests during development and fast CI for integration feedback. Do not run expensive full/release qualification after every edit. Release choreography belongs to standards/RELEASE.md plus the target repository release profile; product-specific PASS1/PASS2 sequences belong in that project rather than the global instruction. Never reuse release evidence from a different candidate HEAD.

For user-facing release qualification, exercise the real primary user surface. Browser products require a real Chromium/Chrome process; component/API/static checks do not substitute for the user action. Keep artifact/SBOM/provenance and other integrity work tied to the final qualified candidate as defined by the project release profile.

For incidents, follow standards/OPERATIONS.md, preserve evidence first, and avoid destructive/irreversible recovery without required approval. For adoption/upgrade, follow standards/ADOPTION.md and preserve project-specific or stricter invariants.

Send Telegram only for a bounded COMPLETE outcome or a genuine BLOCKED state requiring owner action; do not notify for micro-steps. Cursor is retired and is not an implementation path.
