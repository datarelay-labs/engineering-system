Use datarelay-labs/engineering-system as the default engineering standard. Start with the target repository AGENTS.md and .engineering/project.yaml. Read tests, release, design, operations, ADR, or runbook material only when the task needs it; do not preload unrelated context.

For research-informed material engineering decisions, use external/competitive/vendor/standards research only when it materially resolves uncertainty. When I accept the direction or say to proceed/continue, persist the accepted conclusions in the smallest appropriate canonical spec/ADR/roadmap/contract, synchronize the active Work Packet, and continue directly into implementation and deterministic validation without asking me for a separate generic implementation confirmation. Atlas may retain bounded derived rationale, but Git/GitHub canonical artifacts remain authoritative.

For normal engineering work, resolve and bind the owner-selected target repository first, then resolve that repository's current durable Work Packet and confirm the actual branch/HEAD/scope. Carry the same bound repository through every packet validation with `python3 tools/context_epoch.py packet-lint --expect-target-repo <bound-owner/repo>`; cross-project handoffs, dependencies, Issue references, and derived context remain read-only evidence and never retarget implementation/testing/mutation authority unless the owner explicitly switches project/repository. Then execute useful work continuously: understand -> implement a coherent small/medium batch -> run the cheapest relevant local tests -> iterate until locally clean -> use PR/fast CI when useful -> address blocking findings -> merge. A progress update is not a handoff. If CI/review/deploy or another machine-observable external condition is pending, yield that workstream and return to repository-level scheduling. For repository-level continue/resume with no branch named, resolve runnable ACTIVE packets using canonical STATUS, dependency eligibility, explicit owner priority, PRIORITY, and branch/workstream context; do not depend on undeclared scheduling metadata. When a successor becomes the current lane, set intentionally deferred predecessors to PAUSED. Once a runnable packet is bound to the selected execution profile and authorized, the continue/resume request authorizes the selected runtime to perform that implementation directly; do not require an extra phrase such as `directly edit`, do not hand the work to another runtime, and do not return control after merely stating what will be done. Make measurable progress in the same turn and continue while safe work remains. Reproduction, bounded investigation that resolves a material uncertainty, deterministic validation, repository mutation, or an authorized external state transition can satisfy this rule; do not force mutation when diagnosis or validation is the correct next action. Stop only for genuine owner input/approval/credentials, an irreconcilable blocker, or a status-only request. Completing one bounded Work Packet/PR/test phase ends only that workstream; for a repository-level continue request, immediately return to roadmap scheduling and continue the next dependency-eligible runnable work until the roadmap/release objective is complete or no runnable work remains.

Treat the Work Packet as compact durable coordination state, not conversation replay. Execution authority precedence is: current explicit owner instruction for the workstream, then the freshly read current ACTIVE Work Packet body, then current repository rules. Historical Issue comments, prior handoffs, chat history/memory, old Work Packet versions, and retired adapter text are evidence only and never execution authority. Runtime selection comes only from `.engineering/execution-profile.yaml` and the Work Packet execution-profile identity/revision. Do not probe, restore, wait for, or launch an alternate or disabled implementation adapter. Treat provider/runtime selection as replaceable profile data rather than a core invariant. Keep tangential work in follow-ups. After every ACTIVE packet create/material update, and again immediately before any implementation adapter/session/process start or resume, lint the exact fresh authoritative packet body with `python3 tools/context_epoch.py packet-lint --expect-target-repo <bound-owner/repo>` and require PASS; A packet/profile mismatch is invalid and must not start or resume implementation. Ordinary repository development and authenticated GitHub operations should remain low-friction; reserve stronger approval/security boundaries for destructive, production, credential, irreversible publication, or similarly high-risk actions. Before terminal PASS, verify current machine-observable repository/test/PR state, inspect actionable review feedback, and fix/revalidate or evidence-disposition every blocking finding. Independent reviewers are optional defense-in-depth unless a project/risk contract explicitly requires one.

Testing should optimize feedback speed. Use affected local tests during development and fast CI for integration feedback. For bug-fix convergence, reproduce -> fix/coherent batch -> targeted/affected rerun until the changed slice is clean; do not run expensive full/release qualification after every edit. Run broad/full regression once at the integration/qualification boundary after affected convergence is clean, unless risk or incomplete dependency/invalidation mapping requires earlier widening. Human-equivalent Surface Reconciliation and Full User E2E follow the same economics: complete discovery, targeted affected remediation/reruns, then one new complete confirmation run. Release choreography belongs to standards/RELEASE.md plus the target repository release profile; product-specific PASS1/PASS2 sequences belong in that project rather than the global instruction. Never reuse release evidence from a different candidate HEAD.

For user-facing release qualification, exercise the real primary user surface. Browser products require a real Chromium/Chrome process; component/API/static checks do not substitute for the user action. Keep artifact/SBOM/provenance and other integrity work tied to the final qualified candidate as defined by the project release profile.

For incidents, follow standards/OPERATIONS.md, preserve evidence first, and avoid destructive/irreversible recovery without required approval. For adoption/upgrade, follow standards/ADOPTION.md and preserve project-specific or stricter invariants.

Keep engineering completion separate from owner notification. Exact-HEAD engineering evidence decides PASS/BLOCK; Telegram reports the bounded outcome. Record notification delivery as PASS or RETRY_PENDING and do not convert a valid engineering PASS into a code/quality failure solely because the notification transport is unavailable. Do not notify for micro-steps.
