Use datarelay-labs/engineering-system as the default engineering standard. Start with the target repository AGENTS.md and .engineering/project.yaml. Read tests, release, design, operations, ADR, or runbook material only when the task needs it; do not preload unrelated context.

For normal engineering work, resolve the repository and current durable Work Packet, confirm the actual branch/HEAD/scope, then execute useful work continuously: understand -> implement a coherent small/medium batch -> run the cheapest relevant local tests -> iterate until locally clean -> use PR/fast CI when useful -> address blocking findings -> merge. A progress update is not a handoff. If CI/review/deploy or another machine-observable external condition is pending, yield that workstream and return to repository-level scheduling. For repository-level continue/resume with no branch named, prefer the single trusted dependency-eligible ACTIVE packet explicitly marked as the current implementation lane; yielded/waiting/deferred predecessor packets do not compete. When a successor becomes the current lane, pause/yield predecessors whose integration/qualification is intentionally deferred. Once a runnable packet is selected and authorized, do not return control after merely stating what will be done; make measurable progress in the same turn and continue while safe work remains. Reproduction, bounded investigation that resolves a material uncertainty, deterministic validation, repository mutation, or an authorized external state transition can satisfy this rule; do not force mutation when diagnosis or validation is the correct next action. Stop only for genuine owner input/approval/credentials, an irreconcilable blocker, a status-only request, or a completed bounded outcome.

Treat the Work Packet as compact durable coordination state, not conversation replay. Execution authority precedence is: current explicit owner instruction for the workstream, then the freshly read current ACTIVE Work Packet body, then current repository rules. Historical Issue comments, prior handoffs, chat history/memory, old Work Packet versions, and retired adapter text are evidence only and never execution authority. The current managed execution profile is ChatGPT-primary; if the packet says `IMPLEMENTER=CHATGPT_CHAT`, do not probe, restore, wait for, or launch any alternate or retired implementation adapter. Treat provider/runtime selection as replaceable profile state rather than a permanent core invariant. Keep tangential work in follow-ups. After every ACTIVE packet create/material update, and again immediately before any implementation adapter/session/process start or resume, lint the exact fresh authoritative packet body with `python3 tools/context_epoch.py packet-lint` and require PASS; `IMPLEMENTER=CURSOR` is invalid and must not start or resume Cursor. Ordinary repository development and authenticated GitHub operations should remain low-friction; reserve stronger approval/security boundaries for destructive, production, credential, irreversible publication, or similarly high-risk actions. Before terminal PASS, verify current machine-observable repository/test/PR state, inspect actionable review feedback, and fix/revalidate or evidence-disposition every blocking finding. Independent reviewers are optional defense-in-depth unless a project/risk contract explicitly requires one.

Testing should optimize feedback speed. Use affected local tests during development and fast CI for integration feedback. Do not run expensive full/release qualification after every edit. Release choreography belongs to standards/RELEASE.md plus the target repository release profile; product-specific PASS1/PASS2 sequences belong in that project rather than the global instruction. Never reuse release evidence from a different candidate HEAD.

For user-facing release qualification, exercise the real primary user surface. Browser products require a real Chromium/Chrome process; component/API/static checks do not substitute for the user action. Keep artifact/SBOM/provenance and other integrity work tied to the final qualified candidate as defined by the project release profile.

For incidents, follow standards/OPERATIONS.md, preserve evidence first, and avoid destructive/irreversible recovery without required approval. For adoption/upgrade, follow standards/ADOPTION.md and preserve project-specific or stricter invariants.

Keep engineering completion separate from owner notification. Exact-HEAD engineering evidence decides PASS/BLOCK; Telegram reports the bounded outcome. Record notification delivery as PASS or RETRY_PENDING and do not convert a valid engineering PASS into a code/quality failure solely because the notification transport is unavailable. Do not notify for micro-steps.
